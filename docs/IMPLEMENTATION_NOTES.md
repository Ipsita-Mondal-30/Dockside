# Implementation Notes — Scaffold 0.1

## Scope

This scaffold validates the domain and policy direction in memory. It is an executable model for tests and the local evaluation, not a durable runtime.

## Recovery model

The simulator keeps four records separate:

- Partner ground truth: whether a fault applied a booking, whether the response was received, and whether that response was committed.
- Policy-visible evidence: timeouts, lost local commits, authoritative or weak lookup results, ambiguous matches, definitive rejections, and the local pre-send journal.
- Harness decision: confirm success, confirm non-execution, authorize retry, keep the outcome unknown, or escalate.
- Partner-side effects: bookings in the partner ledger attributed to the logical action.

`decideRecovery` reads state, declared capabilities, and evidence. It does not receive the ground-truth object. Scoring reads the ledger and the initial ground-truth record after the decision has been made.

Faults are injected at four lifecycle points: before dispatch, after the partner receives the request and before it applies, after apply and before the response, and after the response is received and before the local success record is committed. A fifth observation is a documented no-effect rejection.

Each logical action keeps one `actionId`. Each dispatch creates a new `attemptId`, and earlier attempts stay in the history. A retry send is possible only from `RETRY_AUTHORIZED` after the policy authorizes it. A pre-send crash stays `READY` and can be dispatched again only when the journal says the side-effect boundary was not crossed. `READY`, `CONFIRMED_SUCCEEDED`, and `ESCALATED` are not rewritten by recovery into another outcome.

Concurrent recovery uses an in-memory version check. Two workers can compute the same decision from one snapshot; only the first commit is applied, so only one dispatch can be authorized.

The partner deduplicates a repeated key only while idempotency is enabled and `idempotencyRetentionValid` is true. An expired window stores a new booking. The naive baseline sends a fresh key on every retry, so partner idempotency does not hide that baseline's duplicates.

## Remaining limitations

- Fault injection models a crash inside one process. There is no durable ledger and no recovery after a real process death.
- The concurrency check is single-threaded compare-and-swap. It is not a row lock, lease, or multi-process race.
- Eventually consistent lookup is a visibility flag. The simulator does not move a replication clock.
- `operator_resolution` is represented on the evidence union. The policy does not apply a human resolution yet, so escalated actions remain escalated.
- No PostgreSQL, Redis, live partner, or LLM is used. An ambiguous action is never sent to a model to decide whether retry is safe.
- The evaluation does not claim exactly-once execution outside this deterministic prototype.

## Debugging protocol

1. Reproduce the failing scenario by ID.
2. Inspect the policy-visible evidence and the partner booking ledger separately.
3. Identify the violated invariant.
4. Fix the narrowest layer responsible (simulator, policy, transition validation, or scorer).
5. Add a regression test before changing other behavior.
6. Run `npm test`, `npm run typecheck`, and `npm run evaluate`.
7. Record the remaining limitation in this file. The evaluation report is regenerated by `npm run evaluate`.
